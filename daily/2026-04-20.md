Module 3 — IAM & Security

  1. Least Privilege Principle

  核心思路：默认拒绝一切，只授予必要权限。

  - 策略从 deny-all 开始，逐步 grant 具体 action + 具体 resource
  - 用 IAM Access Analyzer 扫描过度宽松的策略 (e.g., s3:* on *)
  - 定期审查 unused permissions（Access Advisor 显示每个服务最后使用时间）

  面试角度：别只说"最小权限"，要说如何发现谁权限过大，以及如何收紧。

  ---
  2. IRSA — IAM Roles for Service Accounts

  这是 EKS 上给 Pod 授权的标准模式，非常重要。

  问题背景：Pod 运行在 EC2 节点上，如果用节点级 IAM Role，整个节点上所有 Pod 共享同一个 Role — 权限无法隔离。

  IRSA 解决方案：
  K8s Service Account → OIDC Federation → IAM Role
  3. EKS 集群有 OIDC Provider (URL)
  4. 每个 K8s ServiceAccount 加 annotation: eks.amazonaws.com/role-arn
  5. IAM Role 的 Trust Policy 限定：只允许该集群的该 ServiceAccount assume 这个 Role
  6. Pod 启动时自动注入临时 AWS credentials（via webhook）

  实际用法：
  - ML team A 的 training job Pod → 只能访问 s3://data/team-a/ prefix
  - ML team B 的 Pod → 只能访问 s3://data/team-b/ prefix
  - 完全隔离，无需在代码里写 credentials

  ---
  3. KMS — Key Management Service

  核心用途：管理加密密钥，确保静态数据加密 + 访问可审计。

  ┌─────────────────┬───────────────────────────────────────────┐
  │      场景       │               KMS 使用方式                │
  ├─────────────────┼───────────────────────────────────────────┤
  │ S3 bucket 加密  │ SSE-KMS，每次 PUT/GET 都经过 KMS API call │
  ├─────────────────┼───────────────────────────────────────────┤
  │ EBS volume 加密 │ 创建时指定 CMK                            │
  ├─────────────────┼───────────────────────────────────────────┤
  │ RDS 加密        │ 创建实例时指定 CMK                        │
  ├─────────────────┼───────────────────────────────────────────┤
  │ Secrets Manager │ 自动用 KMS 加密 secret                    │
  └─────────────────┴───────────────────────────────────────────┘

  CMK (Customer Managed Key) vs AWS Managed Key：
  - AWS Managed Key：免费，自动轮换，但你无法控制 key policy
  - CMK：有费用（$1/key/month），但可以自定义谁能 use/admin 这个 key；CloudTrail 记录每次使用 → 合规审计必需

  ---
  4. AWS Organizations + SCPs

  场景：公司有 50+ AWS 账号，如何统一治理？

  AWS Organizations = 账号层级管理（Management Account + OUs + Member Accounts）

  SCP (Service Control Policy) = 作用于 OU 或账号的上限策略（即使账号内 IAM 允许，SCP 不允许也不行）

  典型 SCP 用途：
  - 禁止在未授权 region 创建资源 (只允许 us-east-1, us-west-2)
  - 禁止禁用 CloudTrail
  - 禁止 root 账号直接操作
  - 强制 MFA 删除 S3 object

  面试中强调：SCP 是 guardrail，不是 grant — 它限制上限，具体权限还是靠各账号内的 IAM。

  ---
  5. Multi-Account Strategy

  为什么多账号：blast radius 隔离。prod 账号被误操作不影响 dev；安全账号集中存放 CloudTrail logs。

  常见账号结构：
  Management Account (billing only)
  ├── Security Account (CloudTrail, GuardDuty, Security Hub aggregation)
  ├── Shared Services Account (ECR, VPN, DNS, Transit Gateway hub)
  ├── Production Account
  ├── Staging Account
  └── Dev Account (per team, or shared)

  Identity Center (SSO)：人员统一登录入口，通过 Permission Sets + Account Assignments 控制谁能访问哪个账号的什么角色。不要在每个账号里创建独立 IAM User。

 补强 1：Secrets Manager + External Secrets Operator

  为什么需要这个组合？

  K8s 原生 Secret 有两个问题：
  1. etcd 里默认 base64 存储（≠加密）
  2. 生命周期独立于应用 — secret 轮换后需要手动更新 K8s Secret

  解决方案：把 secret 的 source of truth 放在 AWS Secrets Manager，用 ESO 自动同步到 K8s。

  ---
  完整架构

  ┌─────────────────────────────────────────────────────┐
  │ AWS Secrets Manager                                  │
  │  secret: "prod/myapp/db-password" = "abc123"        │
  │  (KMS CMK 加密存储)                                  │
  └────────────────────┬────────────────────────────────┘
                       │ ESO 定期 poll (每 1h 或按需)
  ┌────────────────────▼────────────────────────────────┐
  │ External Secrets Operator (K8s controller)           │
  │  读取 ExternalSecret CRD → 创建/更新 K8s Secret     │
  └────────────────────┬────────────────────────────────┘
                       │ mount as env var / volume
  ┌────────────────────▼────────────────────────────────┐
  │ Pod                                                  │
  │  env: DB_PASSWORD = "abc123"  (内存里，不在 YAML)   │
  └─────────────────────────────────────────────────────┘

  ---
  核心资源：ExternalSecret CRD

  apiVersion: external-secrets.io/v1beta1
  kind: ExternalSecret
  metadata:
    name: myapp-db-secret
    namespace: team-a
  spec:
    refreshInterval: 1h          # 多久同步一次
    secretStoreRef:
      name: aws-secretsmanager    # 指向哪个 SecretStore
      kind: SecretStore
    target:
      name: myapp-db-secret       # 生成的 K8s Secret 名字
    data:
      - secretKey: password       # K8s Secret 里的 key
        remoteRef:
          key: prod/myapp/db-password   # Secrets Manager 里的路径

  ESO 会自动创建一个 K8s Secret，Pod 正常 mount 即可 — YAML 里永远不出现明文。

  ---
  权限控制：IRSA 收口

  ESO controller 本身通过 IRSA 访问 Secrets Manager：
  - ESO ServiceAccount → IAM Role → 只允许 secretsmanager:GetSecretValue on 指定 secret ARN
  - 每个 namespace 可以有独立的 SecretStore + 独立 IAM Role → 团队隔离

  team-a namespace → SecretStore-A → IAM Role-A → 只能读 prod/team-a/* 的 secret
  team-b namespace → SecretStore-B → IAM Role-B → 只能读 prod/team-b/* 的 secret

  ---
  面试一句话总结

  ▎ "Secrets Manager 是 source of truth（KMS 加密），ESO 是桥梁（自动同步到 K8s Secret），IRSA 控制谁能读哪些 secret。YAML 和 Git 里永远不出现明文，secret
  ▎ 轮换自动生效。"

  Identity Center 解决方案

  ┌─────────────────────────────────────────────────────┐
  │ AWS Identity Center (单一入口)                       │
  │                                                      │
  │  用户目录: 可接 Okta/Azure AD/Google Workspace       │

  └──────────────────────────────────────────────────────┘

  ┌────────────────────┬─────────────────────────────────────────────────────────┐
  │        概念        │                          解释                           │

  └────────────────────┴─────────────────────────────────────────────────────────┘

Module 4 — Storage

  1. S3 — Object Storage

  AWS 最基础的存储服务，AI Infra 里用途极广。

  核心特性：
  - durability: 11个9（数据几乎不会丢）
  - Strong consistency（2020年后，PUT后立即GET一致）
  - 无限容量，按使用付费

  AI Infra 常见用途：

  ┌───────────────────┬──────────────────────────────┐
  │       用途        │             说明             │
  ├───────────────────┼──────────────────────────────┤
  │ Training datasets │ 原始数据长期存放             │
  ├───────────────────┼──────────────────────────────┤
  │ Model artifacts   │ 训练完的模型文件             │
  ├───────────────────┼──────────────────────────────┤
  │ Checkpoints       │ 训练中间状态，crash 后恢复用 │
  ├───────────────────┼──────────────────────────────┤
  │ Pipeline logs     │ 实验记录、metrics            │
  └───────────────────┴──────────────────────────────┘

  Storage Classes（成本优化关键）：

  Standard          → 频繁访问，最贵
  Intelligent-Tiering → 自动在 Standard/IA/Archive 间移动，适合访问模式不确定的数据
  Standard-IA       → 不频繁访问，取数据收费
  Glacier Instant   → 归档，毫秒级取回
  Glacier Deep Archive → 最便宜，取回需要12小时

  性能注意点：
  - 高吞吐场景避免顺序 prefix（如 2026-01-01/, 2026-01-02/）— 同一 prefix 落同一 shard，造成热点
  - 随机 prefix 或 hash prefix 分散到不同 shard，提升并发吞吐

  ---
  2. FSx for Lustre — 高吞吐并行文件系统

  为什么需要它？

  S3 是对象存储，POSIX 语义差，随机读写慢。ML 训练框架（PyTorch DataLoader）需要文件系统语义 + 高吞吐。

  FSx for Lustre 特性：
  - 吞吐：最高 1 TB/s
  - 延迟：sub-millisecond
  - 可直接挂载到 EC2 / EKS Pod（PVC）
  - S3-backed：数据懒加载，第一次访问时从 S3 拉取，后续从 Lustre cache 读

  两种模式：

  ┌────────────┬─────────────────────────────┬────────────────────────┐
  │    模式    │          适用场景           │       数据持久性       │
  ├────────────┼─────────────────────────────┼────────────────────────┤
  │ Scratch    │ 临时训练，便宜，无副本      │ 不持久，硬件故障丢数据 │
  ├────────────┼─────────────────────────────┼────────────────────────┤
  │ Persistent │ 长期共享数据集，跨 job 复用 │ 多副本，持久           │
  └────────────┴─────────────────────────────┴────────────────────────┘

  典型架构：
  S3 (原始数据，长期存储)
      ↓ 懒加载
  FSx for Lustre (高速缓存层，训练时挂载)
      ↓ mount
  GPU Training Pods

  3. EBS — Block Storage

  特点：
  - 挂载到单个 EC2（不共享）
  - 适合数据库、需要低延迟随机读写的场景

  常用类型：

  ┌───────────────────┬──────────────┬────────────────────────────────────────┐
  │       类型        │     IOPS     │                适用场景                │
  ├───────────────────┼──────────────┼────────────────────────────────────────┤
  │ GP3               │ 最高 16,000  │ 默认选择，比 GP2 便宜且可单独配置 IOPS │
  ├───────────────────┼──────────────┼────────────────────────────────────────┤

  ├───────────────────┼──────────────┼────────────────────────────────────────┤
  │ ST1               │ 吞吐型       │ 大文件顺序读写（日志、数仓）           │
  └───────────────────┴──────────────┴────────────────────────────────────────┘

  EKS 里用法： StorageClass ebs.csi.aws.com，创建 PVC 自动 provision EBS volume。

  4. EFS — 共享文件系统

  特点：
  - 多 EC2 / 多 Pod 同时挂载（NFS 协议）
  - 吞吐低于 FSx Lustre，但运维简单
  - 自动扩缩容，无需预设容量

  AI Infra 适用场景：
  - 多个 Pod 共享配置文件、代码
  - 小型共享数据集（不需要 Lustre 级吞吐）
  - 模型 serving：多个 inference Pod 共享同一个模型文件

  1. RDS Aurora

  定位：托管的关系型数据库，MySQL / PostgreSQL 兼容。

  核心架构：
  Writer Instance (1个)
  ├── Read Replica 1
  ├── Read Replica 2  (最多15个)
  └── Read Replica 3

  共享存储层（自动扩容，最大 128TB）

  关键特性：
  - Storage 自动增长 — 无需预设容量，按需扩
  - Failover 快 — 主节点故障，Read Replica 自动提升为 Writer，约 30秒
  - Aurora Serverless v2 — 按 ACU（Aurora Capacity Unit）自动扩缩容，适合流量不稳定的场景；最小可缩到 0.5 ACU，避免闲置浪费

  AI Infra 典型用途：
  - 实验记录（experiment tracking）
  - 训练 job 历史、状态管理
  - 需要复杂 SQL 查询的元数据（JOIN、聚合报表）

  2. DynamoDB

  定位：Serverless key-value / document 数据库，无需管理服务器。

  核心特性：
  - 单digit ms 延迟，无论数据量多大
  - On-demand capacity — 自动扩缩，按请求付费，无需预设 throughput
  - DynamoDB Streams — 数据变更事件流，触发 Lambda 做 event-driven 处理

  数据模型：
  Table: TrainingJobs
    Partition Key: job_id
    Sort Key: created_at

    Attributes: status, model_version, s3_artifact_path, metrics...

  AI Infra 典型用途：
  - Artifact registry（模型版本 → S3 路径的映射）
  - Feature store index（feature key → 存储位置）
  - Pipeline job 状态追踪（高并发写入，ms级查询）

  1. CloudWatch

  AWS 原生监控服务，覆盖 metrics、logs、alarms。

  核心功能：

  ┌────────────────────┬──────────────────────────────────────────────────────────┐
  │        功能        │                           说明                           │
  ├────────────────────┼──────────────────────────────────────────────────────────┤
  │ Metrics            │ AWS 服务自动上报（EC2 CPU、EKS pod、RDS connections 等） │
  ├────────────────────┼──────────────────────────────────────────────────────────┤
  │ Custom Metrics     │ 应用自定义指标，via PutMetricData API                    │
  ├────────────────────┼──────────────────────────────────────────────────────────┤
  │ Logs               │ 应用日志收集，Log Groups 组织，Log Streams 按实例分      │
  ├────────────────────┼──────────────────────────────────────────────────────────┤
  │ Alarms             │ 基于 metric 触发 SNS 通知 / Auto Scaling / Lambda        │
  ├────────────────────┼──────────────────────────────────────────────────────────┤
  │ Log Insights       │ 对日志做 ad-hoc SQL-like 查询                            │
  ├────────────────────┼──────────────────────────────────────────────────────────┤
  │ Container Insights │ EKS pod/node 级别 metrics（CPU、Memory、Network）        │
  └────────────────────┴──────────────────────────────────────────────────────────┘

  EKS 监控典型配置：
  CloudWatch Agent (DaemonSet)
      → 收集 node metrics
  Fluent Bit (DaemonSet)
      → 收集 pod logs → CloudWatch Log Groups
  Container Insights
      → pod/container CPU、Memory、网络

  局限性：
  - 默认 metrics 粒度 1分钟（高分辨率可到10秒，但贵）
  - 跨账号聚合需要额外配置
  - 大规模环境下 Log Insights 查询费用不低

  ---
  2. AWS Cost Explorer + Budgets

  Cost Explorer：
  - 可视化历史花费，按 service、account、tag、region 多维度拆分
  - Tag-based cost allocation 是核心 — 必须强制打 tag（team、env、project）
  - Anomaly Detection — ML 自动检测异常花费，邮件/SNS 告警

  强制 Tag 策略：
  必须打的 tag：
    team: ml-platform / data-eng / infra
    env: prod / staging / dev
    project: gpt-training / recommendation / search
  没有 tag → Cost Explorer 无法拆分 → 不知道谁在花钱。

  Budgets：
  - 设置花费上限，超过阈值触发告警
  - 可触发 SNS → Lambda 自动操作（如停止非关键 EC2）
  - 支持按 service、tag、account 设置独立 budget

  ---
  3. Trusted Advisor & Compute Optimizer

  Trusted Advisor：
  - 扫描账号，给出 Cost / Security / Performance / Fault Tolerance 建议
  - 典型发现：未使用的 EBS volumes、空跑的 EC2、过大的 RDS 实例

  Compute Optimizer：
  - 分析 CloudWatch 历史 metrics，用 ML 推荐更合适的实例类型
  - 覆盖：EC2、EBS、Lambda、ECS
  - 常见发现：m5.4xlarge 实际 CPU 利用率 8% → 建议换 m5.xlarge 省75%

  4. AI Infra 成本结构

  理解花钱在哪，才能优化。

  典型 AI 公司 AWS 月账单构成：

  GPU Compute (EC2 P4d/P5)    ████████████████  60-70%
  Storage (S3 + FSx)          ████             10-15%
  Networking (数据传输)         ███              8-12%
  Databases (Aurora/DynamoDB) ██               5-8%
  其他 (EKS、CloudWatch 等)    █                5%

  GPU 计算是大头，优化重点在这里。

  ---
  5. 成本优化策略

  Spot Instance 策略（最高杠杆）：
  On-Demand GPU: ~$32/hr (p4d.24xlarge)
  Spot GPU:      ~$10/hr  (同实例，节省 ~70%)

  前提：训练代码支持 checkpoint-resume
       Spot interruption handler 优雅 drain
       Karpenter 自动 fallback to On-Demand

  Savings Plans：
  - Compute Savings Plans：承诺1年/3年花费，换取折扣（30~60%）
  - 用于稳定的 baseline 负载（inference serving、常驻服务）
  - Spot 覆盖 burst 训练，Savings Plans 覆盖 baseline

  FSx 生命周期：
  - 训练完立即删除 FSx cluster（按小时计费）
  - checkpoint 同步回 S3 后再删
  - 不训练时 FSx 是纯浪费

  右sizing（Compute Optimizer）：
  - 定期跑 Compute Optimizer，发现低利用率实例
  - Inference 服务常见问题：上线时过度配置，之后没人调整

  ---
  6. 跨账号 Observability 架构

  多账号环境下，如何统一观测：

  每个账号
  ├── CloudWatch → 本地 metrics/logs
  ├── CloudTrail → 发送到 Security Account S3（org-wide trail）
  └── GuardDuty  → findings 聚合到 Security Account

  Security Account
  ├── Security Hub（跨账号 findings 汇总）
  ├── CloudTrail logs（所有账号的操作审计）
  └── Grafana / 第三方（Datadog/Prometheus）做统一 dashboard

  7. 常见面试考点

  Tag 强制化：没有 tag 就没有成本可见性，必须用 Tag Policy（Organizations）强制打 tag — 高频考点

  Spot + checkpoint 组合：GPU Spot 节省70%，但必须配合 checkpoint-resume，这是 AI Infra 成本优化的核心杠杆

  Anomaly Detection：不要等月底账单才发现超支，设置 Cost Anomaly Detection + Budget Alert 做实时预警

  Compute Optimizer vs Trusted Advisor：Optimizer 专注右sizing（ML分析历史用量），Trusted Advisor 更广（安全、容错、性能都覆盖）

  Question 2:

  Your ML team says GPU utilization on training jobs averages only 35%. The infrastructure cost is $500K/month.

  How do you diagnose the root cause, and what levers do you pull to improve utilization and reduce cost?

● 思路有一个方向对，但这题问的是GPU利用率只有35%的根因诊断和修复，Spot 是成本优化手段，不是利用率问题的解法。反馈：

  ⚠️ 核心问题：
  Spot 解决的是成本，不解决利用率低的问题。35% GPU 利用率意味着 GPU 大部分时间在空转 — 需要先找出为什么。

  ┌─────────────────┬──────────────────────────────────┬─────────────────────────────────────────────┐
  │      根因       │               症状               │                    解法                     │
  ├─────────────────┼──────────────────────────────────┼─────────────────────────────────────────────┤
  │ 数据 IO 瓶颈    │ GPU 等数据，CPU/网络满但 GPU 闲  │ S3 换 FSx Lustre，提升数据读取速度          │

  │ batch size 太小 │ GPU 计算太快，没有充分并行       │ 调大 batch size，充分利用显存               │
  └─────────────────┴──────────────────────────────────┴─────────────────────────────────────────────┘

  第二步：成本优化（利用率提升后）

  利用率修复后，再叠加：
  - Spot Instance + checkpoint-resume — 节省70%（你说的这点）
  - Karpenter — 训练完自动缩容，避免 GPU 节点空跑
  - Savings Plans — baseline 负载用 Savings Plans 锁定折扣

  一句话升级版答法：

  ▎ "先用 CloudWatch Container Insights 看 GPU/CPU/网络利用率曲线，判断瓶颈在数据IO、预处理还是 batch size；修复利用率后，再用 Spot + checkpoint
  ▎ 降低计算成本，Karpenter 做自动缩容避免空跑。"
