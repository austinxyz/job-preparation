  1. 先搞清 CIDR 基础数学（1 分钟刷新）

  CIDR 记号 /N 表示前 N 位是网络前缀，后 (32-N) 位是主机地址。

  ┌──────┬──────────┬───────────────────────────┐
  │ CIDR │ 地址总数 │ AWS 可用（扣除 5 个保留） │
  ├──────┼──────────┼───────────────────────────┤
  │ /16  │ 65,536   │ 65,531                    │
  ├──────┼──────────┼───────────────────────────┤
  │ /20  │ 4,096    │ 4,091                     │
  ├──────┼──────────┼───────────────────────────┤
  │ /24  │ 256      │ 251                       │
  ├──────┼──────────┼───────────────────────────┤
  │ /28  │ 16       │ 11（AWS VPC 最小值）      │
  └──────┴──────────┴───────────────────────────┘

  AWS 每个子网会保留 5 个地址：
  - .0 — 网络地址
  - .1 — VPC 路由器
  - .2 — DNS 服务器
  - .3 — AWS 保留（未来用）
  - .255（/24 时）— 广播地址

  所以一个 /24 子网你只有 251 个可用 IP。

  AWS VPC CIDR 的硬限制：最大 /16（65K IPs），最小 /28（16 IPs）。

  ---
  2. 为什么 VPC 用 /16？

  核心原因：VPC 的 primary CIDR 一旦定了就不能改

  你只能扩容（加 secondary CIDR），不能缩小、不能搬迁。选错了就是永久账单。

  /16 是三种选择里最合理的

  ┌────────────┬────────┬─────────────────────────────────────────────────────────────┐
  │    选择    │ 地址数 │                            问题                             │
  ├────────────┼────────┼─────────────────────────────────────────────────────────────┤
  │ /20（4K）  │ 偏小   │ 一个中型 K8s 集群（VPC CNI 每个 pod 吃一个 VPC IP）就能耗尽 │
  ├────────────┼────────┼─────────────────────────────────────────────────────────────┤
  │ /16（65K） │ 刚好   │ 够切 256 个 /24 子网，给各种 workload 分层                  │
  ├────────────┼────────┼─────────────────────────────────────────────────────────────┤
  │ /8（16M）  │ 过大   │ 和 on-prem 撞网段的概率指数上升（见第 5 条）                │
  └────────────┴────────┴─────────────────────────────────────────────────────────────┘

  EKS 的特殊 IP 消耗

  AWS VPC CNI 的行为和 GCP 不一样——每个 pod 占一个 VPC IP 地址（而不是用 overlay 网络）。

  举例：
  - 10 个节点 × 每节点 30 个 pod = 300 个 IP 光是一个 AZ 的 pods
  - 加上 load balancer ENI、RDS 端点、VPC endpoints，再留 buffer
  - /24（251 IP）瞬间就紧了

  所以 /16 VPC 给你足够空间切出能容纳 EKS 密集 pod 的 /23 或 /22 子网。

  ---
  3. 为什么子网用 /24？

  /24 是"默认合理单元"

  - 251 个可用 IP——够一般应用 workload 的一个 AZ
  - 直观：最后一位 octet = 主机号，10.50.10.x 就是 "prod-app-az-a"
  - 数学好算：/24 × 256 个 = 填满一个 /16

  什么时候该偏离 /24？

  ┌──────────────────────────────────────────────────┬────────────────────────────────┐
  │                       场景                       │          建议子网大小          │
  ├──────────────────────────────────────────────────┼────────────────────────────────┤
  │ 普通应用 pods                                    │ /24（251 IP）                  │
  ├──────────────────────────────────────────────────┼────────────────────────────────┤
  │ 高密度 EKS（30+ pods/node × 10+ 节点）           │ /23（507 IP）或 /22（1019 IP） │
  ├──────────────────────────────────────────────────┼────────────────────────────────┤
  │ DB 子网（RDS、Aurora，通常只有 3-6 个 endpoint） │ /27（27 IP）或 /26（59 IP）    │
  ├──────────────────────────────────────────────────┼────────────────────────────────┤
  │ ALB/NAT 公共子网（每个 AZ 一个 ALB + 一个 NAT）  │ /27 就够                       │
  ├──────────────────────────────────────────────────┼────────────────────────────────┤
  │ GPU 节点池（少量大节点，但 EFA + 多 ENI）        │ /24 到 /23                     │
  └──────────────────────────────────────────────────┴────────────────────────────────┘

  关键经验

  宁可一开始把 DB 子网切成 /27，给 app 子网留 /22 的空间——DB endpoint 数量永远不会爆炸，app pods 会。

  ---
  4. "private subnets for workloads, public subnets only for NAT GW / LB"

  三种子网角色（记清路由表差异）

  ┌──────────┬───────────────────────────────────┬──────────────────────────┬─────────────────────────┐
  │ 子网类型 │       默认路由（0.0.0.0/0）       │ 能接受 internet 入流量？ │    能访问 internet？    │
  ├──────────┼───────────────────────────────────┼──────────────────────────┼─────────────────────────┤
  │ Public   │ → IGW（Internet Gateway）         │ ✅（如果 SG 允许）       │ ✅ 直接                 │
  ├──────────┼───────────────────────────────────┼──────────────────────────┼─────────────────────────┤
  │ Private  │ → NAT Gateway（在 public 子网里） │ ❌ internet 无法主动发起 │ ✅ 通过 NAT 出去        │
  ├──────────┼───────────────────────────────────┼──────────────────────────┼─────────────────────────┤
  │ Isolated │ 没有 0.0.0.0/0 路由               │ ❌                       │ ❌ 只能走 VPC Endpoints │
  └──────────┴───────────────────────────────────┴──────────────────────────┴─────────────────────────┘

  为什么 workload 放 private？

  5. 攻击面减小：workload 没有 public IP，internet 扫描扫不到你的 pod
  6. 合规要求：SOC2 / PCI / HIPAA 通常明确要求 data plane 不直接暴露
  7. 稳定出口 IP：NAT GW 有固定 EIP，第三方白名单能写死（数据库、API 合作方都要）
  8. 没有"意外暴露"风险：工程师不可能手滑把 ALB 指到错误的 pod

  为什么 NAT Gateway 要放 public？

  NAT GW 是一个托管服务，它自己需要 IGW 才能出 internet——AWS 把它的 ENI 放在 public 子网里。

  HA 模式：每个 AZ 放一个 NAT GW（不是一个 NAT GW 服务三个 AZ）。原因：
  - NAT GW 是 AZ 绑定的资源
  - 如果 AZ-a 的 NAT GW 挂了，AZ-b/c 的 workload 还是能出网
  - 成本代价：NAT GW 按 AZ 数量计费 + 流量 $0.045/GB 单向

  成本优化对比（AppZen 规模假设）：

  ┌───────────────────────────┬─────────────────┬───────────────────────┐
  │           方案            │      月费       │         容灾          │
  ├───────────────────────────┼─────────────────┼───────────────────────┤
  │ 3 个 NAT GW（每 AZ 一个） │ ~$97 × 3 + 流量 │ AZ 级容灾             │
  ├───────────────────────────┼─────────────────┼───────────────────────┤
  │ 1 个 NAT GW（省钱版）     │ ~$97 + 流量     │ AZ 挂了全 VPC 断网 ❌ │
  └───────────────────────────┴─────────────────┴───────────────────────┘

  生产环境必须每 AZ 一个。

  为什么 ALB 放 public？

  ALB 的前端 ENI 需要能接收 internet 流量 → 必须在 public 子网。

  但 ALB 的 target groups 指向的 pod/instance 是在 private 子网的——这是标准 pattern：public ALB 前端 + private 后端。

  如果是内部流量（比如从一个 VPC 的服务访问另一个 VPC 的内部 API），用 Internal ALB，就可以放 private 子网。

  5. "avoid 10.0.0.0/8 conflicts with on-prem if using Direct Connect" —— 最容易踩的坑

  RFC 1918 三大私有网段

  ┌─────────┬────────────────┬────────┬─────────────────────┐
  │  网段   │      CIDR      │ 地址数 │      常见用途       │
  ├─────────┼────────────────┼────────┼─────────────────────┤
  │ Class A │ 10.0.0.0/8     │ 16M    │ 企业 on-prem 最常用 │
  ├─────────┼────────────────┼────────┼─────────────────────┤
  │ Class B │ 172.16.0.0/12  │ 1M     │ 中等企业            │
  ├─────────┼────────────────┼────────┼─────────────────────┤
  │ Class C │ 192.168.0.0/16 │ 65K    │ 家用 / 小办公室     │
  └─────────┴────────────────┴────────┴─────────────────────┘

  绝大多数企业的 on-prem 网络都已经占用了 10.x.x.x 的大片空间。

  典型场景：
  - 总部 HQ：10.0.0.0/16
  - DC-1：10.50.0.0/16
  - DC-2：10.100.0.0/16
  - VPN 用户：10.200.0.0/16

  为什么冲突是灾难

  当你用 Direct Connect 或 Site-to-Site VPN 把 AWS 和 on-prem 连起来后，路由是不能有重叠的。

  举例：
  - AWS VPC：10.0.0.0/16
  - 公司 HQ：10.0.0.0/16
  - Direct Connect 打开后：AWS 的 pod 想访问 10.0.5.20——路由表不知道该往哪儿送

  结果：
  - 要么 AWS 路由走本地 VPC（访问不到 HQ 的那个 IP）
  - 要么要重新做 NAT（成本 + 复杂度巨大）
  - 要么整个 VPC 要重新 provision（上面说了 primary CIDR 不能改）

  正确做法

  1. 投入前先问公司网络团队要 IPAM 计划（IP Address Management——企业网络部门维护的 IP 分配表）
  2. 只用 on-prem 没用的 /8 切片：比如 HQ 用了 10.0-10.199，你就用 10.240.0.0/16 之后
  3. 用别的 RFC 1918 段：172.16.0.0/12 或 192.168.0.0/16（但这些也可能已被用）
  4. 用 "shared address space"：100.64.0.0/10（RFC 6598，本来是给 ISP 大型 NAT 用的，但 AWS 允许你用作 VPC secondary
  CIDR）——新兴做法，很多大企业在用

  AppZen 场景下的规划建议

  假设 AppZen 多账户结构：

  Prod account        10.50.0.0/16
    ├─ AZ-a public    10.50.0.0/24    (ALB + NAT GW)
    ├─ AZ-b public    10.50.1.0/24
    ├─ AZ-c public    10.50.2.0/24
    ├─ AZ-a private   10.50.10.0/23   (EKS pods，/23 给高密度留空间)
    ├─ AZ-b private   10.50.12.0/23
    ├─ AZ-c private   10.50.14.0/23
    ├─ AZ-a DB        10.50.30.0/27   (RDS 只需要少量 IP)
    ├─ AZ-b DB        10.50.30.32/27
    └─ AZ-c DB        10.50.30.64/27

  Staging account     10.51.0.0/16   (整个 /16 隔离)
  Shared services     10.52.0.0/16   (Direct Connect、VPN 网关、DNS)
  Dev account         10.53.0.0/16
  ... 还能切到 10.99.0.0/16

  关键点：
  - 每个账户用独立 /16，账户间隔离
  - 10.0-10.49 留给 on-prem
  - 10.50-10.99 给 AWS 多账户
  - 10.100+ 未来扩展

  6. 面试答题模板（直接记下来）

  被问"怎么设计 VPC"时，按这个顺序走：

	  1. 先问 CIDR 约束：是否有 on-prem 要连 Direct Connect / VPN？公司 IPAM 给你分了什么段？
	  2. VPC 选 /16：因为 primary CIDR 改不了，先给足够大的空间
	  3. 3 个 AZ 起步：HA 最低要求
	  4. 三层子网结构：
	    - Public（/27 够）——只放 NAT GW + ALB
	    - Private app（/23 到 /24）——EKS pods
	    - Private DB（/27）——RDS/Aurora
	  5. 每 AZ 一个 NAT GW——生产环境必须，AZ 容灾
	  6. VPC Endpoints——S3/DynamoDB（Gateway，免费）+ ECR/SSM（Interface，~$7/mo × endpoints）降低 NAT 流量成本
	  7. 路由表分层：public 子网指 IGW，private 子网指各自 AZ 的 NAT GW
	  8. Security Group 是主要防火墙（stateful），NACLs 只做 subnet 层 deny rule（stateless）

ALB — Application Load Balancer（L7 负载均衡）

  全名：Application Load Balancer
  层级：OSI Layer 7（HTTP/HTTPS）
  职责：基于 URL path、host header、HTTP method 等做路由决策，分发到后端

  核心特性

  - 理解 HTTP 协议：可以按 /api/* 路由到一组 pods，按 /static/* 路由到另一组
  - 支持 target group：一组后端（EC2、IP、Lambda、EKS pod）
  - 支持 WebSocket、HTTP/2、gRPC
  - SSL 终止：在 ALB 上解密 HTTPS，后端可以用 HTTP（减少后端负担）
  - 集成 AWS WAF（Web 应用防火墙）

  和兄弟产品对比

  ┌────────────────────┬───────────────┬───────────────────────────────────────┐
  │   Load Balancer    │     层级      │               适合场景                │
  ├────────────────────┼───────────────┼───────────────────────────────────────┤
  │ ALB（Application） │ L7（HTTP）    │ Web/API 服务、K8s Ingress、按路径路由 │
  ├────────────────────┼───────────────┼───────────────────────────────────────┤
  │ NLB（Network）     │ L4（TCP/UDP） │ 高吞吐、低延迟、静态 IP、非 HTTP 协议 │
  ├────────────────────┼───────────────┼───────────────────────────────────────┤
  │ CLB（Classic）     │ L4 + L7       │ Legacy，新项目别用                    │
  ├────────────────────┼───────────────┼───────────────────────────────────────┤
  │ GWLB（Gateway）    │ L3            │ 把流量透传给防火墙类 appliance        │
  └────────────────────┴───────────────┴───────────────────────────────────────┘

  EKS 场景

  在 EKS 里用 AWS Load Balancer Controller，装好后你写一个 K8s Ingress：
  kind: Ingress
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
  Controller 会自动帮你创建一个 ALB，把 target group 指向 pod IPs。

  EFA — Elastic Fabric Adapter（GPU 集群专用高速网卡）

  全名：Elastic Fabric Adapter
  本质：AWS 专有的网络接口类型，支持 OS-bypass（绕过操作系统内核直接访问网卡）

  为什么存在

  多节点 GPU 训练用 NCCL（NVIDIA Collective Communications Library）做 allreduce 同步 gradient。传统 TCP/IP
  网络延迟太高（几十微秒），在千卡集群上会成为瓶颈。

  EFA 提供类似 RDMA（Remote Direct Memory Access）的能力：
  - 延迟从 ~50μs 降到 ~15μs
  - 带宽可达 3200 Gbps（P5 H100 集群）
  - 减少 CPU 参与网络处理

  使用条件（记住这 3 点）

  1. 只有特定机型支持：P4d（A100）、P5（H100）、Trn1（Trainium）等高端 GPU 机型
  2. 必须用 Cluster Placement Group——强制把节点放在物理上相邻的机架，减少延迟
  3. 必须在同一个 AZ——跨 AZ 延迟立即把 EFA 优势吃掉
  4. SG 要允许所有同 SG 内部的流量（EFA 协议不是标准 TCP）

  面试踩坑

  被问"多节点 GPU 训练吞吐不够怎么查"——第一步就是确认 EFA 启用 + 所有节点同 AZ + placement group 正确。GCP 没有 EFA
  这个概念（GCP 用 GPUDirect RDMA），这是 AWS 特有词汇。

  ---
  ENI — Elastic Network Interface（虚拟网卡）

  全名：Elastic Network Interface
  本质：VPC 里的虚拟网卡，挂载在 EC2 实例或其他 AWS 资源上

  基础模型

  每个 EC2 实例至少有一个 ENI（primary ENI，实例创建时自带）。一个 ENI 有：
  - 一个 MAC 地址（伪硬件地址）
  - 一个或多个 私有 IP（主 IP + secondary IPs）
  - 一个可选的 public IP 或 EIP
  - 关联的 Security Group
  - 所在的 Subnet

  为什么这个概念重要

  EKS 的 VPC CNI 模式：每个 pod 的 IP 是从 ENI 的 secondary IP pool 里分配的。

  例子（c5.xlarge 实例）：
  - 3 个 ENI 上限
  - 每个 ENI 最多 15 个 secondary IPs
  - 理论最多 pod 数：3 × 15 - 3（给 node 本身）= 42 个 pod

  所以选 EC2 机型时要看 ENI 限制表，不然 pod 密度会被网卡上限卡住。Karpenter 会自动算这个。

  相关概念

  - Secondary ENI：你可以手动给一个实例多挂 ENI（比如一个走管理网、一个走业务网）
  - 多 ENI + 多 AZ 的资源：RDS 端点、NAT Gateway、VPC Endpoints 都是本质上在不同 AZ 各放一个 ENI
  - Transit Gateway、NLB、ALB 本身 都是靠 ENI 在 VPC 里"占点"

  ---
  EIP — Elastic IP（可分配的固定公网 IP）

  全名：Elastic IP address
  本质：AWS 账户级别的固定公网 IPv4，你可以"抓住"它并在实例间重分配

  普通 public IP 和 EIP 的区别

  ┌─────────────────────────┬──────────────────────┬────────────────────────────┬────────────────────────────────┐
  │          类型           │        绑定到        │           停机后           │              费用              │
  ├─────────────────────────┼──────────────────────┼────────────────────────────┼────────────────────────────────┤
  │ Auto-assigned public IP │ 实例启动时自动分配   │ IP 消失，重启后换新 IP     │ 免费                           │
  ├─────────────────────────┼──────────────────────┼────────────────────────────┼────────────────────────────────┤
  │ EIP                     │ 账户拥有，你手动关联 │ 保留，可以重新关联到新实例 │ 未关联时 $0.005/hr，关联时免费 │
  └─────────────────────────┴──────────────────────┴────────────────────────────┴────────────────────────────────┘

  为什么需要 EIP

  1. NAT Gateway 的公网 IP——NAT GW 必须用 EIP，才能给第三方白名单一个稳定 IP
  2. 灾难恢复：生产实例挂了，把 EIP 从旧实例解开、关联到新实例，DNS 不用改
  3. 合规要求：某些服务商/政府对接需要"从这个 IP 来"的流量白名单
  4. 回到同一 IP 的需求：比如站点级 SSL 证书绑 IP（罕见但存在）

  重要限制

  - 默认每个 region 只能拥有 5 个 EIP（需申请提额）
  - 未关联的 EIP 会收费——这是 AWS 经典"忘记删资源就烧钱"坑
  - 现在 AWS 对新分配 EIP 收费 $0.005/hr 了（2024 起），以前免费关联实例的待遇没了

  SSM — Systems Manager（AWS 运维工具套件）

  全名：AWS Systems Manager
  本质：一整套运维管理工具的总称，不是单一服务

  最常用的 5 个模块

  ┌─────────────────┬────────────────────────────────────────┬───────────────────────────────────────────────┐
  │      模块       │                  职责                  │                   典型场景                    │
  ├─────────────────┼────────────────────────────────────────┼───────────────────────────────────────────────┤
  │ Session Manager │ 替代 SSH/RDP 登录 EC2                  │ 无需开放 port 22 也能登录实例（通过 AWS API） │
  ├─────────────────┼────────────────────────────────────────┼───────────────────────────────────────────────┤
  │ Parameter Store │ 存配置和密钥（类似 Vault/K8s Secrets） │ 环境变量、API keys、数据库连接串              │
  ├─────────────────┼────────────────────────────────────────┼───────────────────────────────────────────────┤
  │ Patch Manager   │ 批量打补丁                             │ EC2 合规性维护                                │
  ├─────────────────┼────────────────────────────────────────┼───────────────────────────────────────────────┤
  │ Run Command     │ 在多台 EC2 上并发执行 shell/PowerShell │ 批量运维脚本                                  │
  ├─────────────────┼────────────────────────────────────────┼───────────────────────────────────────────────┤
  │ Automation      │ 运维 runbook                           │ 故障自愈、例行操作自动化                      │
  └─────────────────┴────────────────────────────────────────┴───────────────────────────────────────────────┘

  为什么面试常问

  Session Manager 是现代 AWS 运维的标配，你应该能讲出：
  - "我们所有 EC2 都禁用 SSH port 22，通过 Session Manager 登录——登录过程 IAM 授权 + CloudTrail 审计 + 无需开放 0.0.0.0/0:22"
  - "Session Manager 需要 EC2 有 SSM Agent + IAM 角色挂了 AmazonSSMManagedInstanceCore 策略"

  一些坑

  - Session Manager 要求实例能访问 ssm.<region>.amazonaws.com 和 ssmmessages.<region>.amazonaws.com——private 子网必须有 VPC
  Interface Endpoint 才能用
  - Parameter Store 免费版有速率限制（40 TPS）；SecureString（KMS 加密）类型比 standard 贵很多

  和 Secrets Manager 的区别

  ┌──────────┬───────────────────────────────────────────────┬─────────────────────────────────┐
  │   维度   │              SSM Parameter Store              │         Secrets Manager         │
  ├──────────┼───────────────────────────────────────────────┼─────────────────────────────────┤
  │ 价格     │ 便宜（Standard 免费，Advanced $0.05/参数/月） │ 贵 $0.40/密钥/月                │
  ├──────────┼───────────────────────────────────────────────┼─────────────────────────────────┤
  │ 自动轮换 │ ❌                                            │ ✅（原生支持 RDS 轮换）         │
  ├──────────┼───────────────────────────────────────────────┼─────────────────────────────────┤
  │ 大小限制 │ 4KB（Standard）/ 8KB（Advanced）              │ 64KB                            │
  ├──────────┼───────────────────────────────────────────────┼─────────────────────────────────┤
  │ 适合场景 │ 配置 + 非关键 secret                          │ 数据库密码、API key（需要轮换） │
  └──────────┴───────────────────────────────────────────────┴─────────────────────────────────┘

  ---
  NACLs — Network ACLs（子网级防火墙）

  全名：Network Access Control Lists
  本质：子网级别的 stateless 防火墙

  和 Security Group 的对比（核心！）

  ┌──────────┬──────────────────────────────────┬──────────────────────────────────────────────┐
  │   维度   │       Security Group（SG）       │                     NACL                     │
  ├──────────┼──────────────────────────────────┼──────────────────────────────────────────────┤
  │ 作用范围 │ 实例（ENI）级别                  │ 子网级别                                     │
  ├──────────┼──────────────────────────────────┼──────────────────────────────────────────────┤
  │ 状态     │ Stateful——允许出就自动允许回     │ Stateless——出/入要分别写规则                 │
  ├──────────┼──────────────────────────────────┼──────────────────────────────────────────────┤
  │ 规则类型 │ 只能写 Allow                     │ 可以写 Allow 和 Deny                         │
  ├──────────┼──────────────────────────────────┼──────────────────────────────────────────────┤
  │ 规则顺序 │ 所有规则并行评估                 │ 按 rule number 顺序，先匹配先生效            │
  ├──────────┼──────────────────────────────────┼──────────────────────────────────────────────┤
  │ 默认行为 │ 默认全部拒绝（empty = deny all） │ 默认 allow all（新建时），自定义要显式加规则 │
  ├──────────┼──────────────────────────────────┼──────────────────────────────────────────────┤
  │ 附加方式 │ 一个 ENI 可以挂最多 5 个 SG      │ 一个 subnet 只能挂 1 个 NACL                 │
  └──────────┴──────────────────────────────────┴──────────────────────────────────────────────┘

  "Stateful vs Stateless" 的实际含义

  Stateful（SG）：
  规则：允许出向 443 端口
  行为：pod → 访问 S3（443）✅ 允许
        S3 返回包 → pod ✅ 自动允许（SG 记住了出向连接）

  Stateless（NACL）：
  规则：允许出向 443 端口
  行为：pod → 访问 S3（443）✅ 允许（匹配出向规则）
        S3 返回包 → pod ❌ 如果没有入向规则允许 "ephemeral ports 1024-65535" 就会被拦！

  这就是为什么 NACL 一般只用来做粗粒度的子网级 deny，而不是日常流量控制。

  什么时候用 NACL

  99% 场景用 SG 就够了。NACL 用于：

  1. 显式阻止特定 IP/IP 段——SG 写不了 deny，只能 NACL
    - 例："永久 block 这个攻击 IP"
  2. 子网层级的 compliance boundary——DB 子网加一条 NACL 规则："只允许来自 app 子网 CIDR 的入向流量"
  3. 防御 SG 配置错误的兜底——即使工程师把 SG 配成 allow 0.0.0.0/0，NACL 还能拦一层

  规则顺序的坑

  NACL 按 rule number 从小到大评估，先匹配先生效：
  Rule 100: DENY 1.2.3.4/32
  Rule 200: ALLOW 0.0.0.0/0
  Rule 100 先命中，1.2.3.4 被拦；其他 IP 继续走到 Rule 200，放行。

  如果写反了：
  Rule 100: ALLOW 0.0.0.0/0
  Rule 200: DENY 1.2.3.4/32   ← 永远不会命中

  默认 NACL vs 自定义 NACL

  - Default NACL（VPC 创建时自带）：默认 allow all in/out——等于没限制
  - Custom NACL（你自己建的）：默认 deny all in/out——要显式加规则

  Private 子网里的 workload（EKS pod、EC2 instance）没有公网 IP，但它们需要访问：

  ┌───────────────────────┬────────────────────────────────────────────┐
  │    需要访问的目标     │                  典型场景                  │
  ├───────────────────────┼────────────────────────────────────────────┤
  │ S3                    │ 读数据集、存模型 artifact、CloudWatch Logs │
  ├───────────────────────┼────────────────────────────────────────────┤
  │ ECR                   │ 拉 container image                         │
  ├───────────────────────┼────────────────────────────────────────────┤
  │ DynamoDB              │ 元数据存储                                 │
  ├───────────────────────┼────────────────────────────────────────────┤
  │ CloudWatch            │ 发 metrics、logs                           │
  ├───────────────────────┼────────────────────────────────────────────┤
  │ Secrets Manager / SSM │ 读 secrets、配置                           │
  ├───────────────────────┼────────────────────────────────────────────┤
  │ 第三方 API            │ Stripe、GitHub、Datadog、OpenAI API…       │
  └───────────────────────┴────────────────────────────────────────────┘

  这些流量怎么出去？ 有 3 条路径，成本和安全性差很多。

  ---
  三条 Egress 路径

  路径 A — NAT Gateway（全部走公网）

  流程：
  Private pod → NAT GW（public subnet）→ IGW → Internet → S3（或任何 target）

  费用：
  - $0.045/hr per NAT GW（24 × 30 × 0.045 ≈ $32/月 per AZ）
  - $0.045/GB processed（单向——出 + 入都按这个费率）

  3 AZ 生产环境：3 × $32 = ~$97/月空转成本 + 流量费

  例子：月处理 10 TB 流量 → 10,000 × $0.045 × 2（出+入）= $900/月 流量费

  路径 B — Gateway Endpoint（免费）

  只支持两个服务：S3 和 DynamoDB（就这两个，没有别的）

  流程：
  Private pod → VPC 内的 Gateway Endpoint → AWS 骨干网 → S3

  费用：完全免费——没有小时费，没有流量费，没有任何隐藏成本

  实现：VPC 里加一个 VPC Endpoint（类型选 "Gateway"），在 private subnet 的路由表里加一条路由：S3 的 prefix list → 该
  Endpoint。之后 pod 访问 S3 的流量会被路由走 Endpoint，而不是 NAT GW。

  这是 AWS 最划算的免费午餐。生产环境必开。

  路径 C — Interface Endpoint（按量收费，但比 NAT 便宜）

  几乎所有其他 AWS 服务都有 Interface Endpoint：ECR、CloudWatch、SSM、Secrets
  Manager、KMS、STS、SNS、SQS、Kinesis、Lambda……完整列表约 200 个。

  流程：
  Private pod → VPC 里的 Interface Endpoint（一个 ENI，在你的子网里）→ AWS 骨干网 → 目标服务

  费用：
  - $0.01/hr × AZ 数 × Endpoint 数（每 AZ 每个 Endpoint ≈ $7.3/月）
  - $0.01/GB processed（比 NAT 便宜 4.5 倍）

  3 AZ + 5 个 Endpoints（ECR api、ECR dkr、CloudWatch Logs、Secrets Manager、SSM）：
  - 固定成本：3 × 5 × $7.3 = ~$110/月
  - 流量成本：假设 1 TB → 1000 × $0.01 = $10/月
  - 总计：~$120/月

  ---
  实际决策逻辑（最关键部分）

  黄金原则：流量能走 AWS 内部骨干的，就绝不走公网。

  第一步 — 无脑开 Gateway Endpoint

  S3 和 DynamoDB 的 Gateway Endpoint 完全免费 + 更安全 + 更快。生产环境没开是配置错误。

  第二步 — 根据流量大小决定 Interface Endpoint

  用决策公式：

  当某个 AWS 服务的月流量 > 临界值时，开 Interface Endpoint 划算

  临界点计算（单 AZ）：
  - Interface Endpoint 固定成本：$7.3/月 ，流量 $0.01/GB
  - NAT GW 流量成本：$0.045/GB（+ 公摊固定成本）
  - 节省 = traffic_GB × ($0.045 - $0.01) - $7.3
  - 临界流量 = $7.3 ÷ $0.035 = ~210 GB/月/AZ

  **也就是：**某服务月流量 > 210 GB（单 AZ），就该开 Interface Endpoint。

  第三步 — 剩下的走 NAT Gateway

  - 访问第三方服务（Stripe、GitHub、Datadog、OpenAI API）——别无选择
  - 低流量的 AWS 服务（用得少，开 Endpoint 不值）
  - 临时 / 一次性访问

  ---
  三个最常见的坑

  坑 1：Interface Endpoint 的 Private DNS 必须开启

  默认情况下访问 secretsmanager.us-west-2.amazonaws.com 会解析到公网 IP——你开了 Endpoint 但流量还是走 NAT，白花钱。

  必须：创建 Interface Endpoint 时勾选 "Enable Private DNS Name"。勾了之后，VPC 内 DNS 会把这个域名解析到 Endpoint 的 private
  IP。

  怎么验证：在 pod 里 nslookup secretsmanager.us-west-2.amazonaws.com，返回的 IP 应该在你的 subnet CIDR 范围内。

  坑 2：Gateway Endpoint 必须更新每个相关子网的路由表

  创建 S3 Gateway Endpoint 时 AWS 会问你"选择哪些路由表"——别忘记把所有 private 子网的路由表都勾上。没勾的子网的流量还是走 NAT。

  坑 3：Interface Endpoint 的 Security Group

  Interface Endpoint 本质是一个 ENI，ENI 关联 SG。默认 SG 可能不允许来自 VPC 内部的 443 入流量——要加入向 443 允许 VPC CIDR
  的规则，否则 pod 访问 Endpoint 会超时。

  ---
  延伸思考：什么时候 不 需要 NAT Gateway？

  完全零公网访问的架构（极致安全的合规场景）：

	  1. 所有 AWS 服务都开 Interface/Gateway Endpoint
	  2. 第三方 API 通过 AWS PrivateLink 合作方（越来越多 SaaS 支持，比如 Datadog、Snowflake）
	  3. 不支持 PrivateLink 的第三方走专门的 egress 代理 VPC（所有出网流量集中过一个 squid/Envoy 代理，统一审计）

  这叫 "NAT-less VPC" 模式。实现难度大，但一些金融、医疗客户会要求。

  面试里能提到这个选项显得有深度，但不用深入。

好，多 VPC / 多账户 CIDR 规划——这是在百万美元错误边界上做决策，很多大厂工程师都栽过跟头。

  ---
  核心问题：为什么 CIDR 规划一旦做错就痛苦到极点

  记住这 4 条：

  1. VPC primary CIDR 永久不能改——改它的唯一办法是 provision 新 VPC + 全部搬迁
  2. 两个 VPC 如果 CIDR 有重叠，VPC peering 和 Transit Gateway 都无法建立路由——AWS 会直接拒绝
  3. Direct Connect / VPN 连接 on-prem 时，AWS VPC 和 on-prem 也不能 CIDR 重叠——同样的路由冲突问题
  4. K8s pod 用 VPC CNI 时，每个 pod 吃一个 VPC IP——IP 耗尽是常见事故

  "VPC primary CIDR 不能改" 是整个规划的起点。day 0 随便画一个 10.0.0.0/16，day 180 公司上 Direct Connect 发现 on-prem
  已经占了这个段——你要么把这个 VPC 整个重建，要么把 on-prem 重新编号（几乎不可能）。

  ---
  三层规划的思维模型

  把 IP 规划想成三个嵌套的决策：

  Level 1: 企业全局 IPAM（整个 10.0.0.0/8 怎么切）
    ↓
  Level 2: Account / VPC 分配（每个账户拿一个 /16）
    ↓
  Level 3: Subnet 切分（一个 /16 VPC 切成 public/private/DB 子网）

  Level 3 我们上一节讲过了（VPC 内部 /24 切分、public/private/DB 三层）。
  本节重点：Level 1 和 Level 2。

  ---
  Level 1：企业 IPAM——整个 10.0.0.0/8 怎么切

  10.0.0.0/8 有 1677 万 个地址。一般企业的切法是按用途预留大块，然后在块内分配。

  经典企业 IPAM 模板

  10.0.0.0/11    (10.0-10.31)     → 公司 HQ + 办公室网络（on-prem 核心）
  10.32.0.0/11   (10.32-10.63)    → 数据中心（on-prem DCs，legacy workload）
  10.64.0.0/11   (10.64-10.95)    → AWS 生产环境
  10.96.0.0/11   (10.96-10.127)   → AWS 非生产（staging、dev、sandbox）
  10.128.0.0/11  (10.128-10.159)  → GCP / Azure / 其他云
  10.160.0.0/11  (10.160-10.191)  → 未来扩展（新 region、新业务线）
  10.192.0.0/10  (10.192-10.255)  → 长期保留（10-20 年视野）

  每个 /11 = 32 个 /16 = 32 个 VPC（或 32 个账户 × 1 VPC）。

  为什么这样切

  1. 环境隔离 → AWS prod 和 non-prod 永远不会撞段
  2. 云商隔离 → AWS 和 GCP 以后要联通时，CIDR 天然不冲突
  3. on-prem 优先 → on-prem 已经占用的段先留好，云方案从未占用的段开始
  4. 视野够长 → 预留保留块 = 10 年内不用重新规划

  关键约定：谁动保留段，谁必须走 IPAM 变更审批

  这不是技术决策，是组织纪律。没有这个纪律，5 年后一定有人偷偷占了保留段导致下次扩张撞车。

  ---
  Level 2：Account / VPC 分配——你具体拿哪个 /16

  AWS 多账户标准结构（AWS Well-Architected 推荐）

  Organization Root
    ├─ Management Account       (billing + Organizations 管理，不跑 workload)
    ├─ Security Account         (CloudTrail 集中、GuardDuty、Security Hub)
    ├─ Log Archive Account      (所有 CloudTrail/VPC Flow Logs 归档)
    ├─ Shared Services Account  (Transit Gateway、集中 VPN、DNS、CI/CD)
    ├─ Production Account(s)    (生产 workload)
    ├─ Staging Account
    ├─ Development Account
    └─ Sandbox Account          (开发者个人试验田)

  为什么多账户而不是单账户多 VPC：
  - Blast radius 隔离：一个账户被攻破 ≠ 全部被攻破
  - IAM 边界天然隔离：账户之间没有默认信任
  - 成本分账清晰：每个账户单独 billing
  - 服务 quota 独立：一个账户的 EC2 上限不影响别的账户

  CIDR 分配示例（用上面的 Level 1 模板）

  AWS 生产段 10.64.0.0/11 怎么用：

  Production US-West-2:
    10.64.0.0/16    Production primary VPC（EKS、apps、DBs）
    10.65.0.0/16    Production data VPC（数据处理、ETL）
    10.66.0.0/16    保留（未来新 region 或新 workload）

  Staging:
    10.96.0.0/16    Staging primary VPC
    10.97.0.0/16    保留

  Shared Services:
    10.100.0.0/16   Shared services VPC（Transit Gateway attach、集中 DNS）

  Sandbox / Dev:
    10.110.0.0/16   Dev 个人 VPC 1
    10.111.0.0/16   Dev 个人 VPC 2
    ...

  每个 VPC 的 /16 内部再切（Level 3 内容）

  前面讲过了：public /24 × 3 AZ、private app /23 × 3 AZ、private DB /27 × 3 AZ……

  ---
  Secondary CIDR——Primary CIDR 不够用的唯一救命稻草

  VPC primary CIDR 不能改，但 secondary CIDR 可以加。

  规则

  - 每个 VPC 最多 4 个 secondary CIDR blocks（hard limit，不能提额）
  - Secondary CIDR 可以用：
    - RFC 1918 私有段（10.x、172.16-31.x、192.168.x）
    - RFC 6598 的 100.64.0.0/10（shared address space）
  - Secondary CIDR 不能：
    - 和 primary 重叠
    - 和其他 secondary 重叠
    - 和已连接的 VPC peering / TGW 路由重叠

  主要用途 1：EKS pod 密度爆炸的救命稻草

  AWS VPC CNI 默认每个 pod 吃一个 VPC IP。举例场景：
  VPC: 10.64.0.0/16  (65K IPs)
    Private app subnet /23 × 3 AZ = 3 × 507 = 1521 pods 容量

  如果 workload 涨到 5000 pods（实测 LLM inference 常见），subnet 不够用。

  解法：加一个 secondary CIDR 100.64.0.0/16，专门给 pods 用。EKS 配置 custom networking：pod IP 从 100.64.x.x 分配，节点 IP
  还从原 10.64.x.x 分配。

  主要用途 2：合并 M&A 场景

  公司 A 收购公司 B，两家都用 10.0.0.0/16——冲突。短期内把 B 的 VPC 加一个 secondary 100.64.0.0/16，逐步把 workload 迁移过去。

  为什么 100.64.0.0/10 这个段这么好用

  - RFC 6598 定义为"shared address space"，给 ISP 的 carrier-grade NAT 用
  - 几乎没有企业在 on-prem 占用它
  - AWS 明确支持作为 VPC secondary CIDR
  - 10.x 段被占满后，这是"紧急扩展池"

  ---
  连接 VPC 的三种方式（决定 CIDR 设计）

  方式 A：VPC Peering（点对点）

  VPC A (10.64.0.0/16) ←→ VPC B (10.65.0.0/16)

  规则：
  - CIDR 不能重叠
  - 不支持传递路由：A 连 B、B 连 C，A 不能通过 B 访问 C

  适用：少量 VPC（< 5 个），偶尔跨 VPC 调用。

  方式 B：Transit Gateway（TGW，星形）

             Transit Gateway
                    |
       ┌─────┬──────┼──────┬─────┐
     VPC A  VPC B  VPC C  VPC D  On-prem（via Direct Connect）

  规则：
  - 所有连到 TGW 的 VPC / on-prem 网段 都不能重叠
  - TGW 路由表可以细粒度控制哪些 VPC 能互相访问（route table association + propagation）
  - 支持传递路由——这是它的主要卖点

  成本：
  - TGW 本身：$0.05/hr (~$36/月)
  - Attachment：$0.05/hr per attachment (~$36/月 per VPC)
  - 流量：$0.02/GB

  适用：> 5 个 VPC 的规模、或需要连 on-prem / 多账户。这是现代企业标准方案。

  方式 C：VPC Sharing via RAM（Resource Access Manager）

  核心思路：一个中央账户拥有一个大 VPC，其他账户通过 RAM 共享某些 subnet。

  Shared Services Account (owns VPC 10.64.0.0/16)
    ↓ shares subnets via RAM
  Production Account (uses shared subnets，只能用 subnet，不能改 VPC 设置)

  优势：
  - 多账户之间天然互通（共用 VPC）
  - 统一 CIDR 管理，不用 TGW 路由
  - 比 TGW 便宜很多

  劣势：
  - 账户之间不再有 network boundary——blast radius 更大
  - 某些服务在共享 subnet 里有限制
  - VPC 所有权集中，其他账户不能改路由、SG 等

  适用：同一团队拥有的多个账户，比如一个产品线下的 prod/staging/dev。不适合完全隔离的业务。

  决策速查

  ┌─────────────────────────────┬─────────────────────────────┐
  │            场景             │             选              │
  ├─────────────────────────────┼─────────────────────────────┤
  │ 2-3 个 VPC，独立业务        │ VPC Peering                 │
  ├─────────────────────────────┼─────────────────────────────┤
  │ 一个团队多账户，想省 TGW 费 │ RAM 共享 subnet             │
  ├─────────────────────────────┼─────────────────────────────┤
  │ 企业级多账户 + 连接 on-prem │ Transit Gateway（标准答案） │
  └─────────────────────────────┴─────────────────────────────┘

  ---
  Hybrid Cloud：Direct Connect / VPN + CIDR 纪律

  一旦你要连 on-prem，所有规则升级为 "AWS 和 on-prem 的所有 CIDR 都不能重叠"。

  最常见的错误场景

  Day 0：
  - 工程师拍脑袋用 10.0.0.0/16 给 AWS VPC
  - 公司没有 Direct Connect，AWS 和 on-prem 完全隔离

  Day 180：
  - 业务要求 AWS 访问 on-prem 的数据库
  - 网络团队要建 Direct Connect
  - 发现 on-prem HQ 正好也用 10.0.0.0/16——撞了

  修复成本：
  - Option A：重建整个 AWS VPC，搬迁所有 workload（生产事故级别）
  - Option B：用 NAT 做双向翻译（维护噩梦，每次新加服务都要配 NAT 规则）
  - Option C：给 AWS VPC 加 secondary CIDR，新 workload 上 secondary，旧的逐步迁移（半搞定状态会持续数年）

  正确做法（Day 0）：
  - 投入 AWS 前先和网络团队要 on-prem 的 IPAM 表
  - 永远假设你会连 on-prem——按这个假设规划 CIDR
  - 从未被 on-prem 占用的段开始

  AWS IPAM 服务（托管 IPAM）

  AWS 有一个托管 IPAM 服务（2021 推出），可以：
  - 定义层级化的 IP 池（Top-level Pool → Regional Pool → VPC Pool）
  - 自动发现未使用段、冲突检测
  - 跨账户共享 IP 管理
  - 和 VPC 创建流程集成（让 VPC 自动从池里分配）

  大企业必用，省掉手动维护 Confluence 表格。

  ---
  1. AWS IAM 心智模型（GCP 过来的人必须重置）

  AWS IAM 和 GCP IAM 的核心哲学完全不同：

  ┌───────────────┬─────────────────────────────────────────┬───────────────────────────────────────────────────────────────┐
  │     维度      │                 GCP IAM                 │                            AWS IAM                            │
  ├───────────────┼─────────────────────────────────────────┼───────────────────────────────────────────────────────────────┤
  │ 绑定方向      │ 资源绑定身份（IAM binding on resource） │ 身份绑定策略（policy attached to identity）+ 资源也可以有策略 │
  ├───────────────┼─────────────────────────────────────────┼───────────────────────────────────────────────────────────────┤
  │ 策略语言      │ 简单：role + member + resource          │ 复杂 JSON：Effect、Action、Resource、Condition                │
  ├───────────────┼─────────────────────────────────────────┼───────────────────────────────────────────────────────────────┤
  │ 评估顺序      │ 资源层合并所有 binding                  │ Explicit Deny > Explicit Allow > Default Deny                 │
  ├───────────────┼─────────────────────────────────────────┼───────────────────────────────────────────────────────────────┤
  │ ID 类型       │ Service Account 是第一公民              │ Role 是第一公民（短期凭证）                                   │
  ├───────────────┼─────────────────────────────────────────┼───────────────────────────────────────────────────────────────┤
  │ 跨账户/跨项目 │ 共享 VPC 或跨项目 binding               │ AssumeRole（显式切换身份）                                    │
  └───────────────┴─────────────────────────────────────────┴───────────────────────────────────────────────────────────────┘

  AWS 的复杂度很真实。AWS IAM 是"拒绝即死"的语言 —— 任何一条 explicit deny 会压倒所有 allow。

  ---
  2. 四种 IAM 主体（Principal）

  ┌────────────────────┬───────────────────────────────────┬──────────────────────┬───────────────────┐
  │        主体        │               用途                │       凭证类型       │       寿命        │
  ├────────────────────┼───────────────────────────────────┼──────────────────────┼───────────────────┤
  │ Root User          │ 账户所有者                        │ 密码 / access key    │ 永久              │
  ├────────────────────┼───────────────────────────────────┼──────────────────────┼───────────────────┤
  │ IAM User           │ 人类工程师                        │ 密码 + access key    │ 永久              │
  ├────────────────────┼───────────────────────────────────┼──────────────────────┼───────────────────┤
  │ IAM Role           │ 服务、pod、跨账户、federated 身份 │ 临时凭证（STS 签发） │ 15 分钟到 12 小时 │
  ├────────────────────┼───────────────────────────────────┼──────────────────────┼───────────────────┤
  │ Federated Identity │ SSO、OIDC、SAML 过来的身份        │ 临时凭证             │ 短期              │
  └────────────────────┴───────────────────────────────────┴──────────────────────┴───────────────────┘

  现代 AWS 实践的核心规则

  生产环境不要用 IAM User。 所有 workload 用 Role。人类用 Identity Center（AWS SSO） 联合登录后拿临时凭证。

  原因：
  - Access key 泄露是 AWS 头号事故来源
  - Role 发的临时凭证 15 分钟-12 小时过期，泄露也风险可控
  - Role 有 trust policy——谁能 assume 有明确规则

  ---
  3. IAM 策略语言（JSON）

  Policy 三种类型

  ┌─────────────────────┬──────────────────────────────┬──────────────────────────────────┐
  │        类型         │            附加到            │               用途               │
  ├─────────────────────┼──────────────────────────────┼──────────────────────────────────┤
  │ Identity-based      │ User / Role                  │ 这个身份能做什么                 │
  ├─────────────────────┼──────────────────────────────┼──────────────────────────────────┤
  │ Resource-based      │ S3 bucket / SQS / KMS key 等 │ 这个资源允许谁访问               │
  ├─────────────────────┼──────────────────────────────┼──────────────────────────────────┤
  │ Permission Boundary │ User / Role                  │ 限制这个身份最多能做什么（上限） │
  └─────────────────────┴──────────────────────────────┴──────────────────────────────────┘

  最基础的 Policy 结构

  {
    "Version": "2012-10-17",
    "Statement": [
      {
        "Sid": "ReadOnlyFraudBucket",
        "Effect": "Allow",
        "Action": [
          "s3:GetObject",
          "s3:ListBucket"
        ],
        "Resource": [
          "arn:aws:s3:::appzen-ds-fraud",
          "arn:aws:s3:::appzen-ds-fraud/*"
        ],
        "Condition": {
          "StringLike": {
            "s3:prefix": "datasets/*"
          }
        }
      }
    ]
  }

  关键要素：
  - Action：API 操作，service:OperationName 格式（s3:GetObject、ec2:DescribeInstances）
  - Resource：ARN（Amazon Resource Name）—— arn:aws:s3:::bucket-name/path/*
  - Condition：附加约束，最强大的功能（源 IP、时间、MFA、VPC endpoint、请求字段等）

  Policy 评估逻辑（面试常考）

  用户的一个请求是否被允许：

  1. 检查所有适用 policy（identity-based + resource-based + SCP + Permission Boundary）
  2. 如果有任何一条 Explicit Deny → 拒绝（不可覆盖）
  3. 否则如果有 Explicit Allow → 允许
  4. 否则 → 拒绝（default deny）

  关键点：
  - Deny 永远压倒 Allow——不管多少 allow，一个 deny 就完事
  - 默认拒绝——policy 里不写 = 禁止
  - SCP (Service Control Policy) 在 Organizations 层——即使账户内 policy 允许，SCP 拒绝也不行

  ---
  4. Role 和 Trust Policy（IRSA 的基础）

  Role 有两个 policy：

	  1. Trust Policy（信任策略）：谁可以 assume 这个 role
	  2. Permission Policy（权限策略）：assume 后能做什么

  Trust Policy 示例

  {
    "Version": "2012-10-17",
    "Statement": [
      {
        "Effect": "Allow",
        "Principal": {
          "Service": "ec2.amazonaws.com"
        },
        "Action": "sts:AssumeRole"
      }
    ]
  }

  这条 trust policy 说：EC2 服务可以 assume 这个 role——这是给 EC2 instance profile 用的。

  其他常见 trust principals

  // AWS 服务
  "Principal": { "Service": "lambda.amazonaws.com" }

  // 另一个 AWS 账户
  "Principal": { "AWS": "arn:aws:iam::123456789012:root" }

  // 具体的 IAM user / role
  "Principal": { "AWS": "arn:aws:iam::123456789012:role/deployer" }

  // 联合身份（OIDC、SAML）— IRSA 用这个
  "Principal": { "Federated": "arn:aws:iam::123456789012:oidc-provider/..." }

  7. 核心问题：EKS pod 怎么访问 AWS 资源？

  问题：pod 要读 S3、写 DynamoDB、调 KMS——需要 AWS 凭证。这些凭证从哪来？

  历史上三种方案，演进路径：

  方案 A（最糟）：在 pod 里放 IAM user 的 access key

  env:
  - name: AWS_ACCESS_KEY_ID
    value: AKIA...
  - name: AWS_SECRET_ACCESS_KEY
    value: xxx

  为什么糟：
  - access key 永久存在——泄露后果严重
  - 所有 pod 共享同一身份——无法追踪
  - 轮换困难——改了 key 所有 pod 要重启
  - 代码库 commit access key 是 AWS 账户被黑头号路径

  不要用。这是入门级安全错误。

  方案 B（旧标准）：EC2 Node 级 IAM Role

  把 IAM role 挂在 EKS 的 EC2 node 上（instance profile）。Node 上所有 pod 通过 EC2 元数据服务（IMDS，169.254.169.254）
  拿到临时凭证。

  致命缺陷：
  - 所有 pod 共享同一个 role 的权限——team A 的 pod 能读 team B 的 S3 bucket
  - 权限只能并集（node role 要包含所有 workload 需要的权限）——违反最小权限
  - 无法按 pod 做审计——CloudTrail 只看到 node 的 role，不知道哪个 pod 做的操作

  这种方式在 2019 年 IRSA 发布前是默认，现在是反模式。

  方案 C（现代标准）：IRSA（IAM Roles for Service Accounts）

  核心思路：每个 K8s ServiceAccount 对应一个 IAM Role。pod 通过 ServiceAccount → OIDC token → AssumeRoleWithWebIdentity → 拿到
  role 的临时凭证。

  ---
  6. IRSA 深度解析

  机制流程图
	
	  1. EKS 集群启动时，AWS 给它一个 OIDC provider URL（例如 oidc.eks.us-west-2.amazonaws.com/id/ABC123）
	  2. 你在 IAM 把这个 OIDC provider 注册为 trusted identity provider
	  3. 你创建 IAM Role，trust policy 说：「信任来自这个 OIDC provider 的 token，只要 sub claim 是
	  system:serviceaccount:<namespace>:<sa_name>」
	  4. 创建 K8s ServiceAccount，加 annotation: eks.amazonaws.com/role-arn=arn:...
	  5. Pod 使用这个 ServiceAccount 启动
	  6. EKS mutating webhook 在 pod 里注入:
	     - 环境变量 AWS_ROLE_ARN + AWS_WEB_IDENTITY_TOKEN_FILE
	     - 一个 projected volume mount 包含 JWT token
	  7. Pod 启动 AWS SDK 时，SDK 自动读 token 文件，调 sts:AssumeRoleWithWebIdentity
	  8. STS 验证 token（签名来自 EKS OIDC）、检查 sub claim 匹配
	  9. STS 返回临时凭证（默认 1h，可配到 12h）
	  10. SDK 自动用临时凭证访问 S3/DynamoDB 等
	  11. Token 快过期时 SDK 自动续

  Trust Policy 关键部分

  {
    "Version": "2012-10-17",
    "Statement": [
      {
        "Effect": "Allow",
        "Principal": {
          "Federated": "arn:aws:iam::ACCOUNT_ID:oidc-provider/oidc.eks.us-west-2.amazonaws.com/id/ABC123"
        },
        "Action": "sts:AssumeRoleWithWebIdentity",
        "Condition": {
          "StringEquals": {
            "oidc.eks.us-west-2.amazonaws.com/id/ABC123:sub": "system:serviceaccount:fraud:fraud-reader",
            "oidc.eks.us-west-2.amazonaws.com/id/ABC123:aud": "sts.amazonaws.com"
          }
        }
      }
    ]
  }

  关键点解读：
  - Federated：这个 OIDC provider（EKS 集群）可以发起 assume
  - sub claim：只允许来自 namespace fraud 的 ServiceAccount fraud-reader —— namespace 隔离就是在这里实现的
  - aud claim：token audience，防止其他 OIDC token 被滥用

  ServiceAccount 配置

  apiVersion: v1
  kind: ServiceAccount
  metadata:
    name: fraud-reader
    namespace: fraud
    annotations:
      eks.amazonaws.com/role-arn: arn:aws:iam::ACCOUNT_ID:role/fraud-s3-reader

  这个 annotation 是触发 IRSA 的关键。pod 引用这个 SA 后自动获得 role 的凭证。

  Pod 使用

  apiVersion: v1
  kind: Pod
  metadata:
    name: fraud-training-job
    namespace: fraud
  spec:
    serviceAccountName: fraud-reader  # ← 引用 SA
    containers:
    - name: trainer
      image: ...
      # 不需要任何 AWS 凭证环境变量！
      # SDK 自动找 AWS_WEB_IDENTITY_TOKEN_FILE

  IRSA 的本质优势

  1. Per-pod identity：每个 SA = 一个 role = 独立权限
  2. Namespace 隔离天然实现：trust policy 的 sub claim 限制
  3. 可审计：CloudTrail 记录 assumed role 的名字，能追到具体 ServiceAccount
  4. 无长期凭证：临时凭证 1h 过期
  5. 符合最小权限：每个 role 只给它需要的权限

  6. EKS Pod Identity（2023 年的新方案）

  2023 年 AWS 推出 EKS Pod Identity，进一步简化 IRSA。

  和 IRSA 的差异

  ┌────────────────────┬────────────────────────────────────┬───────────────────────────────────────┐
  │        维度        │                IRSA                │             Pod Identity              │
  ├────────────────────┼────────────────────────────────────┼───────────────────────────────────────┤
  │ OIDC provider 配置 │ 每个集群要手动注册                 │ 不需要                                │
  ├────────────────────┼────────────────────────────────────┼───────────────────────────────────────┤
  │ Trust policy       │ 复杂（OIDC claim + sub + aud）     │ 简单：只信任 pods.eks.amazonaws.com   │
  ├────────────────────┼────────────────────────────────────┼───────────────────────────────────────┤
  │ 跨集群迁移         │ 要改 trust policy 的 OIDC provider │ 跨集群可移植                          │
  ├────────────────────┼────────────────────────────────────┼───────────────────────────────────────┤
  │ Agent              │ 不需要                             │ 需要 eks-pod-identity-agent DaemonSet │
  ├────────────────────┼────────────────────────────────────┼───────────────────────────────────────┤
  │ 发布年             │ 2019                               │ 2023                                  │
  └────────────────────┴────────────────────────────────────┴───────────────────────────────────────┘

  Pod Identity 的 Trust Policy

  {
    "Version": "2012-10-17",
    "Statement": [
      {
        "Effect": "Allow",
        "Principal": {
          "Service": "pods.eks.amazonaws.com"
        },
        "Action": [
          "sts:AssumeRole",
          "sts:TagSession"
        ]
      }
    ]
  }

  超级简洁——但 AWS 怎么知道给哪个 pod 哪个 role？通过 EKS Pod Identity Association：

  aws eks create-pod-identity-association \
    --cluster-name prod-eks \
    --namespace fraud \
    --service-account fraud-reader \
    --role-arn arn:aws:iam::...:role/fraud-s3-reader

  这个 association 独立于 IAM，存在 EKS 层面。

  什么时候用哪个

  - 新建集群 + AWS-only：用 Pod Identity，更简单
  - 已有大量 IRSA + 要兼容：继续用 IRSA
  - 跨云 / OIDC 给其他平台也用：用 IRSA（OIDC 是标准）

  面试里两个都能讲是加分项。

  8. AppZen 场景端到端实现（Q2 的完整答案）

  场景回顾：三个团队（fraud、OCR、expense），各自 S3 bucket，要求 namespace 隔离 + 只读自己的 + 无长期凭证 + 可审计。

  步骤 1：EKS 集群配置 OIDC

  # EKS 创建时 AWS 已经给了 OIDC issuer URL
  # 在 IAM 注册为 OIDC provider（eksctl 或 Terraform 自动做）

  步骤 2：每个团队一个 IAM Role

  Fraud role（fraud-s3-role）：

  Permission policy:
  {
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::appzen-ds-fraud",
        "arn:aws:s3:::appzen-ds-fraud/*"
      ]
    }]
  }

  Trust policy（限制 namespace + SA）：
  {
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::ACCOUNT:oidc-provider/oidc.eks..."
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "oidc.eks.../:sub": "system:serviceaccount:fraud:fraud-workload",
        "oidc.eks.../:aud": "sts.amazonaws.com"
      }
    }
  }

  OCR role（ocr-s3-role）和 Expense role（expense-s3-role）类似，各自只授权自己的 bucket，trust policy 限制自己的
  namespace:SA。

  步骤 3：每个 namespace 一个 ServiceAccount

  # fraud namespace
  apiVersion: v1
  kind: ServiceAccount
  metadata:
    name: fraud-workload
    namespace: fraud
    annotations:
      eks.amazonaws.com/role-arn: arn:aws:iam::ACCOUNT:role/fraud-s3-role
  ---
  # ocr namespace 类似，SA 名可以不一样
  apiVersion: v1
  kind: ServiceAccount
  metadata:
    name: ocr-workload
    namespace: ocr
    annotations:
      eks.amazonaws.com/role-arn: arn:aws:iam::ACCOUNT:role/ocr-s3-role
  ---
  # expense namespace 类似

  步骤 4：Pod 使用对应 SA

  # fraud namespace 里的 pod
  apiVersion: apps/v1
  kind: Deployment
  metadata:
    namespace: fraud
  spec:
    template:
      spec:
        serviceAccountName: fraud-workload  # ← 不写这个就默认 SA，没 IAM 权限
        containers:
        - name: trainer
          image: fraud-trainer:v1

  步骤 5：防御性的 bucket policy（双重保险）

  在 S3 bucket 本身也加 policy，明确限制来源 role：

  // appzen-ds-fraud bucket policy
  {
    "Statement": [{
      "Sid": "DenyExceptFraudRole",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::appzen-ds-fraud",
        "arn:aws:s3:::appzen-ds-fraud/*"
      ],
      "Condition": {
        "StringNotEquals": {
          "aws:PrincipalArn": "arn:aws:iam::ACCOUNT:role/fraud-s3-role"
        }
      }
    }]
  }

  为什么要这层：即使 OCR 的 pod 不小心拿到了 fraud role 的 ARN（通过 bug 或人为错误），S3 bucket policy 还会再 deny
  一层。Defense in depth。

  步骤 6：审计

  - CloudTrail 自动记录所有 API 调用，包含 assumed role ARN——能看到是 fraud-s3-role assume 成功后访问了
  s3://appzen-ds-fraud/xxx
  - 加一层 S3 Access Logs 或 CloudTrail data events（收费但可审计每个对象访问）
  - IAM Access Analyzer 扫描哪些 role 有过度权限（未使用的 action）

  可以追到哪个 pod？ CloudTrail 里的 userIdentity.sessionContext.sessionIssuer 会显示原始 role ARN + session name（session name
   默认是 SA 名字），进一步结合 K8s audit log 可以追到具体 pod。

  步骤 7：放到 Terraform 里

  module "fraud_irsa" {
    source  = "terraform-aws-modules/iam/aws//modules/iam-role-for-service-accounts-eks"
    role_name = "fraud-s3-role"

    role_policy_arns = {
      policy = aws_iam_policy.fraud_s3_policy.arn
    }

    oidc_providers = {
      main = {
        provider_arn               = module.eks.oidc_provider_arn
        namespace_service_accounts = ["fraud:fraud-workload"]
      }
    }
  }

  这是典型 IaC 写法，整个 IRSA setup 可以被 review、版本化、重建。

  9. 常见坑和 best practices

  坑 1：忘记在 pod spec 写 serviceAccountName

  不写的话 pod 用 namespace 的 default SA，没 IRSA，AWS SDK 会转去读 IMDS（node role），可能拿到过高权限。

  防御：用 EKS Pod Security Standards 或 Gatekeeper/Kyverno 强制要求所有 pod 必须显式 serviceAccountName。

  坑 2：Node role 有过多权限

  Node role 应该只包含：AmazonEKSWorkerNodePolicy + AmazonEKS_CNI_Policy + AmazonEC2ContainerRegistryReadOnly。不要把 S3
  权限加到 node role——否则忘 IRSA 的 pod 能"兜底"拿到 node 权限。

  进阶：用 IMDSv2 + hop limit = 1 阻止 pod 访问 IMDS，强制所有 AWS access 走 IRSA。

  坑 3：Trust policy 的 sub claim 写错

  system:serviceaccount: 这个前缀必须有，格式是 system:serviceaccount:<ns>:<sa_name>。很多人漏了 system: 前缀导致 assume
  失败，错误信息是 AccessDenied: Not authorized to perform sts:AssumeRoleWithWebIdentity——看起来像权限问题实际是 sub 不匹配。

  坑 4：Wildcard trust policy

  不要这样写：
  "oidc.eks.../:sub": "system:serviceaccount:fraud:*"

  允许 fraud namespace 里任何 SA assume——破坏隔离。如果需要多个 SA，用 StringLike + 精确 SA 名列表。

  坑 5：Role 共享跨 namespace

  见过团队把一个 role 给多个 namespace 的 SA 用——sub claim 用 StringLike 允许多个 pattern——这打破 IRSA 的核心价值（per-SA
  identity）。每个工作负载身份 = 一个独立 role。

  坑 6：临时凭证过期配置

  默认 1 小时。长时间运行的 job（training）token 过期会中断。两个配置：
	  1. SA annotation: eks.amazonaws.com/token-expiration: "86400" (token 有效期)
	  2. Role 的 Max Session Duration: 最多 12 小时

  AWS SDK 会自动续，但版本要新（< 2018 的 SDK 不支持）。

  12. 多账户场景（AppZen 规模会遇到）

  跨账户 role：Cross-Account AssumeRole

  场景：AppZen 生产账户的 EKS pod 要读 另一个账户的 S3 bucket（比如 data-lake 账户）。

  步骤：
	  1. Data-lake 账户创建 role（cross-account-reader），trust policy 信任 Prod 账户的 fraud-s3-role:
	  "Principal": { "AWS": "arn:aws:iam::PROD_ACCOUNT:role/fraud-s3-role" },
	  "Action": "sts:AssumeRole"
	  2. Prod 的 fraud-s3-role 的 permission policy 加 assume 权限:
	  "Action": "sts:AssumeRole",
	  "Resource": "arn:aws:iam::DATA_LAKE_ACCOUNT:role/cross-account-reader"
	  3. Pod 代码里用 SDK 先 assume_role 拿跨账户凭证，再访问 S3

  链式 assume：EKS pod (via IRSA) → Prod role → Cross-account role → S3

  SCP（Service Control Policy）

  Organizations 层的"天花板"，限制整个账户内任何 role / user 能做什么。典型用途：
  - Deny iam:* 对 production 账户——没人能改 IAM policy 直接从账户
  - Deny 在非批准 region 创建资源
  - Deny 关 CloudTrail

  SCP 不给任何权限，只限制上限。

  Permission Boundary

  Role 级别的"天花板"。场景：你想让 dev team 能自己创建 role，但创建出来的 role 不能超过某个权限范围。

  - Dev team 有 iam:CreateRole 权限
  - 但策略要求新建 role 必须 attach permission boundary（例如 DeveloperBoundary）
  - 新建的 role 即使 permission policy 写得再宽，实际权限 = permission policy ∩ permission boundary

  ---
  11. KMS 集成（数据加密）

  基本原则：生产环境 S3、EBS、RDS 都应该用 KMS 加密。

  两种 KMS key

  - AWS Managed Key（aws/s3、aws/rds）：AWS 自动管理，免费，但跨账户共享、访问审计能力有限
  - Customer Managed Key (CMK)：你创建的 key，完全控制 key policy 和轮换

  S3 + KMS + IRSA 的权限链

  让 pod 能读一个 KMS 加密的 S3 对象，需要：
  1. S3 权限：s3:GetObject on bucket/object
  2. KMS 权限：kms:Decrypt on the key
  3. KMS key policy：也要明确允许这个 role 使用 key（resource-based + identity-based 都必须通过）

  常见错误：IAM role 有 s3:GetObject，但没有 kms:Decrypt——GetObject 返回 AccessDenied，但根源是 KMS。
